## Context

QuickFox 的产品承诺是键盘优先的跨平台快速启动器。当前实现已经有搜索框、结果列表、后台索引、托盘设置入口和设置页，但最近截图显示启动器在真实桌面中呈现为带系统标题栏的大透明窗口，桌面背景和文件文字会穿透到产品视觉中。首次索引未完成时，用户输入后只看到“文件索引尚未建立”，没有进度、恢复路径或可继续使用的能力提示。

现有代码还把 launcher 和 settings 放在同一个 React `App` 视图和同一个 Tauri main window 中。上一轮设置页优化需要系统窗口控件和可调整大小能力，但这些需求会伤害启动器的轻量浮层体验。因此本轮设计重点是拆清产品状态和窗口语义，而不是继续调搜索框尺寸。

## Goals / Non-Goals

**Goals:**

- 让启动器首屏在真实桌面环境中看起来像紧凑、可信、可立即输入的 launcher。
- 让首次索引、索引构建中、索引失败、无结果都有清楚的用户反馈和下一步动作。
- 让后台索引状态变化能刷新前端状态，避免用户停留在过期的“索引尚未建立”反馈。
- 保持设置页可以使用系统窗口控件、调整大小和完整配置布局。
- 增加截图或浏览器级视觉验收，覆盖这类单元测试无法发现的产品问题。

**Non-Goals:**

- 不重做完整品牌视觉系统。
- 不在本轮引入第三方 UI 组件库。
- 不实现完整命令安全重设计，只保留现有命令预览路径。
- 不实现公开第三方插件 API。
- 不改变搜索排序算法、索引扫描策略或 Provider 合同，除非为状态反馈暴露必要事件。

## Decisions

1. **启动器和设置页使用分离的窗口语义。**
   启动器应是紧凑、无干扰、内容自包裹的浮层；设置页应是可调整大小、有系统窗口控件的管理窗口。实现可以选择两个 Tauri window，也可以保留一个 window 但在进入 launcher/settings 时动态切换 decorations、size、transparent、shadow 和 resizable 等属性。优先推荐两个窗口，因为状态边界清楚，测试和手工验收也更直接。

2. **启动器首屏不放营销说明，但允许首次/异常状态的轻量帮助。**
   空输入仍不显示大块结果区；但当索引未建立、构建中、失败或无结果时，结果区域可以显示一条紧凑状态行，包含状态、可用替代能力和恢复动作。例如“索引正在建立，仍可使用计算器和网页前缀”，并提供“刷新索引”或“打开设置”的动作。

3. **前端用统一的 launcher status model 渲染状态。**
   不把状态文案散落在 JSX 条件分支里。建议提取 `LauncherStatus` 或等价 helper，把 query、results、index status、command enabled、web prefixes 等信息收敛为可渲染状态：empty、searching、results、noResults、indexPreparing、indexFailed、commandDisabled。这样测试能直接覆盖状态转换。

4. **索引状态通过事件或轮询保持新鲜。**
   后端在后台索引完成/失败时应向 main window 发出索引状态事件；前端监听后更新状态，并在当前 query 仍存在时重新搜索。若事件实现受限，可先用短期轮询作为过渡，但 tasks 中应记录后续移除轮询的条件。

5. **状态动作必须通过 Rust core 执行。**
   “刷新索引”“打开设置”“打开权限设置”等动作仍通过 Tauri command/event 进入 Rust core 或现有 action 分发，避免前端绕过平台适配边界。

6. **视觉验收使用本地浏览器/桌面截图补足单元测试。**
   前端单元测试验证语义和状态；浏览器或 Tauri 手工截图验证真实窗口形态、背景污染、文本溢出和状态行布局。截图验收不要求像素级 golden，但必须记录关键场景和可接受标准。

## Risks / Trade-offs

- [Risk] 两个 Tauri window 会增加窗口状态同步复杂度。→ 优先封装窗口 adapter，并让托盘“显示 QuickFox”和“设置”分别调用明确入口。
- [Risk] 动态切换同一窗口属性在不同平台表现不一致。→ 如果选择单窗口方案，必须把 macOS/Windows/Linux 行为列入手工验收；若失败则退回双窗口方案。
- [Risk] 首屏帮助过多会破坏 launcher 的轻量感。→ 只在首次、异常或 query 后状态中显示帮助，正常空输入保持极简。
- [Risk] 索引完成后自动重新搜索可能造成输入过程中的结果跳动。→ 仅在 query 未变化且用户仍停留 launcher 时刷新；保留键盘选中重置规则。
- [Risk] 浏览器页面不能完全模拟 Tauri 透明窗口和系统标题栏。→ 浏览器验收覆盖布局，Tauri 手工验收覆盖真实窗口 chrome 和透明背景。

## Migration Plan

1. 先补前端状态模型和测试，确保当前单窗口实现下状态反馈正确。
2. 再拆分或动态调整窗口模型，补 Rust/Tauri 测试和手工验收清单。
3. 最后加索引状态事件和视觉验收记录。
4. 若窗口拆分在某平台不稳定，可保留设置页当前系统窗口能力，先将启动器改为非透明、内容自包裹的可接受形态，再开后续 change 做双窗口完善。

## Open Questions

- 实现阶段需要根据 Tauri 2 当前 API 决定采用“双窗口”还是“单窗口动态属性”。推荐先 spike 双窗口，因为它更符合产品语义。
- “打开设置”是否允许在索引异常状态行内出现。当前设计允许，因为它不是常驻启动器设置按钮，而是异常恢复动作。
